## Architecture Patterns

- **MonoBehaviour singletons** for managers (GameManager, CombatStats)
- **ScriptableObject** for data (CombatConfig, EnemyData, CharacterData, LevelData, TileTypeData)
- **Event-driven combat** — MatchDetector finds matches, CombatResolver translates to CombatEffects, subscribers react
- **ISaveStorage interface** with JSON file and in-memory implementations
- **EditMode tests** using NUnit — no Play Mode tests yet

## Conventions

- One system at a time — test in Unity immediately after changes
- Commit every working state
- Namespace everything under `Soulstream.Matchmancer`
- Assembly definitions: `Matchmancer.Runtime`, `Matchmancer.Editor`
- 7x9 board, portrait orientation, 60fps target

## Design Pillars

1. Readable at a glance (60px icon test)
2. Dark fantasy = restraint, not noise
3. Every mechanic teaches the world (lore-connected)
4. One system, proven, then the next
5. Ship the ugly truth, then polish

## What NOT To Do

- Never prompt "build me a match-3 game" — one system at a time
- No feature unless it earns its complexity
- No casino energy aesthetics
- Polish and art come after core mechanics work
- Do not build two things at once
